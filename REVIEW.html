Approve — The OKD detection and stream-targeting logic is correct, and matches the right variant of the job name for each check (raw name for okd-scos, e2e--stripped name for the RHCOS substring heuristics). Only a non-blocking open question about historical OKD streams and a stylistic nit remain.

What this PR does

  • Adds OKD detection to the "should match os version" Ginkgo test in test/extended/ci/job_names.go, based on ClusterVersion.Status.Desired.Version containing okd-scos.
  • Fails the test if job name and cluster OKD-ness disagree on the okd-scos substring.
  • validateStandaloneNodeOS takes both the raw and e2e--stripped job names: the raw name for the okd-scos check (since that substring lives in the job's variant, ahead of the split point), the stripped name for the RHCOS-stream substring heuristics (avoiding false matches from the org/repo/branch portion of the name).
  • OKD clusters now target the centos-10 OS image stream instead of falling through the RHCOS 9/10 heuristics used for OCP.
  • The ClusterVersion fetch lives entirely inside validateStandaloneNodeOS, so MicroShift/HyperShift clusters never reach it.

Findings

Nits

nittwo Failf branches could be one XOR check

test/extended/ci/job_names.go:272-277

The two if isOKD && !... / if !isOKD && ... blocks implement an XOR and could collapse to if isOKD != strings.Contains(...). Current form is arguably clearer given the distinct failure messages, so this is stylistic only.

if isOKD && !strings.Contains(rawJobName, "okd-scos") {
    e2e.Failf("cluster is OKD but job name %q does not contain 'okd-scos'", jobName)
}
if !isOKD && strings.Contains(rawJobName, "okd-scos") {
    e2e.Failf("cluster is not OKD but job name %q contains 'okd-scos'", jobName)
}

Questions

questiondoes OKD always target centos-10 regardless of install version?

test/extended/ci/job_names.go:280-298 (validateStandaloneNodeOS)

For isOKD == true, the function hardcodes targetStream = "centos-10" unconditionally. Non-OKD clusters get a version-based fallback (4.x installs preserved as rhel-9 even after upgrade to 5.x) via the default: branch, but OKD skips that fallback entirely. If OKD ever had a pre-centos-10 stream, an OKD cluster on that older stream and not yet upgraded would fail this check. Not necessarily wrong, but unexplained in the PR description or code.

switch {
case isOKD:
    targetStream = "centos-10"
case strings.Contains(jobName, "rhcos10"):
    targetStream = "rhel-10"
case strings.Contains(jobName, "rhcos9"):
    targetStream = "rhel-9"
case strings.Contains(jobName, "-runc"):
    targetStream = "rhel-9"
default:

Things I checked and was fine with

  • validateStandaloneNodeOS(oc *exutil.CLI, jobName, rawJobName string): rawJobName (pre e2e- split) is used only for the okd-scos/isOKD check, since that substring lives in the job's variant, ahead of the e2e- split point. jobName (post-split) is used for the rhcos10/rhcos9/-runc switch and the later rhcos9-10 mixed-cluster check, matching the split's original purpose of avoiding false substring matches from the org/repo/branch portion of the job name.
  • switch precedence in validateStandaloneNodeOS: the isOKD case correctly takes precedence over the rhcos10/rhcos9/-runc substring checks, avoiding misclassification of an OKD job name that also happens to contain e.g. rhcos10.
  • The ClusterVersion fetch lives entirely inside validateStandaloneNodeOS, which is only reached on the non-MicroShift/non-HyperShift path — MicroShift and HyperShift clusters never touch it.
  • No unit tests expected/needed — this is itself a live-cluster e2e assertion, consistent with the rest of the file.
  • No changes to shared library code or other call sites; blast radius limited to this one Ginkgo It.

Open questions for the author

  • Has OKD ever used a stream other than centos-10 (e.g. during an internal 9→10-style transition)? If not, might be worth a one-line comment explaining why the version-based fallback is skipped for OKD.
