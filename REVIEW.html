Verdict

Approve

The fix is correctly reasoned and well tested. It replaces a span-based duration calculation (which double-counted gaps between disjoint CVO-reporting episodes) with a proper interval-merge/union calculation, matching the PR's stated intent and backed by solid RCA evidence of the bug it caused in production. I traced the merge algorithm and updated test expectations by hand and found them consistent; I could not execute go build/go test in this sandbox (no go binary available), so CI should be the final correctness gate.

What this PR does

  • Replaces fromAndTo (which computed latest_end - earliest_start across all intervals naming an operator in a CVO Progressing message) with summarizeWaitingIntervals, which sorts intervals and merges overlapping/adjacent ones into distinct episodes.
  • The "waiting" duration is now the sum of merged episode durations, not the full span between first and last observation — fixing overcounting when CVO reports on the same operator across multiple disjoint episodes (e.g. due to CVO restarts).
  • Failure and flake diagnostic messages are enriched with total duration, episode count, longest episode, full observation span, and each merged episode's time range.
  • Scope is tightly contained to one file pair: operators.go and operators_test.go in legacycvomonitortests.
  • Existing Test_updateCOWaiting expectations were updated to reflect the corrected semantics (not just an API rename), and a new table-driven Test_summarizeWaitingIntervals covers merge, adjacency, invalid intervals, and edge cases.

Things I checked and was fine with

  • Merge algorithm correctness by hand-tracing: sort by (From, To) ascending, then merge when interval.From is not strictly after the last episode's To — correctly handles overlap, adjacency, and full containment (a nested interval doesn't shrink To since only max is applied).
  • No aliasing bug: sorted := append(monitorapi.Intervals(nil), intervals...) copies before sorting; last := &summary.episodes[...] mutates only the freshly built episodes slice, not the caller's input.
  • Invalid-interval filtering (From.IsZero() or To.Before(From)) happens inside the merge loop after sorting — doesn't affect sort correctness and correctly excludes garbage.
  • Zero-duration "point" intervals (From == To) are treated as valid zero-length episodes, matching the "separated point does not fill gap" test's intent.
  • fromAndTo is fully removed; a repo-wide grep for it returns nothing — no dangling references.
  • A repo-wide grep for COWaiting/summarizeWaitingIntervals/waitingIntervalSummary outside this package returns nothing — the change is fully self-contained.
  • Hand-verified the updated Test_updateCOWaiting expectations, e.g. "incremental one" changes from the old next + 2*time.Minute (which spanned a 3-hour gap) to the new 5 * time.Minute (3min + 2min, correctly excluding the gap) — this is exactly the bug being fixed.
  • Test_summarizeWaitingIntervals table-driven cases (disjoint point vs. real episode, overlap+adjacency with out-of-order input, multiple episodes without double-counting, invalid-interval filtering, all-empty/all-invalid) hand-traced against the implementation — all consistent.
