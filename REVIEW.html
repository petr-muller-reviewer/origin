Approve

Solid, focused change that closes a real gap in test reliability. The platform detection logic is correct, the framework integration follows established patterns, and the test suite covers the important edge cases. No blocking issues found.

What this PR does

  • Adds platform detection in PrepareCollection by reading the Infrastructure CR, so the haproxy monitor test only runs where haproxy static pods are actually deployed (BareMetal, OpenStack, vSphere with API VIP and OpenShift-managed LB).
  • On unsupported platforms, returns NotSupportedError from every phase, which the framework converts into JUnit skips — replacing today's vacuous passes.
  • On supported platforms, scanAllOperatorPods now fails hard when zero haproxy pods are found, catching silent rot of namespace/label assumptions.
  • Handles MicroShift (no Infrastructure CR) gracefully via IsNotFound check, and checks both the deprecated singular APIServerInternalIP and the current plural APIServerInternalIPs field.
  • Adds comprehensive unit tests for the platform detection logic covering all three supported platforms and their edge cases.

Findings

No blocking or should-fix issues. Three nits:

nit Zero-container gap in scanAllOperatorPods

pkg/monitortests/network/onpremhaproxy/monitortest.go:109-127

The new check guards against zero pods, but if pods exist and none contains a haproxy container (filtered at line 117), the function returns nil. The label selector makes this unlikely in practice, but counting scanned containers and failing on zero would fully close the gap.

if len(infraPods) == 0 {
    return fmt.Errorf("found no haproxy pods to scan: ...")
}
// ... later:
if container.Name != "haproxy" {
    continue
}

nit Test coverage for LB type on OpenStack and vSphere

pkg/monitortests/network/onpremhaproxy/platform_test.go:81-92

The user-managed loadbalancer test case only covers BareMetal. The production code applies the same LB-type gating to all three platforms. Adding equivalent cases for OpenStack and vSphere would prevent a regression if someone modifies the switch arms independently.

nit Switch case repetition in platform detection

pkg/monitortests/network/onpremhaproxy/platform.go:26-49

The three platform branches are near-identical. Go's type system makes abstraction difficult here (different concrete status types), so the repetition is reasonable. Worth noting that if a fourth platform ever gains haproxy support, this switch needs updating — but the test file makes the supported set explicit, so missing it would be caught.

Things I checked and was fine with

  • NotSupportedError integration follows the established pattern used by disruptionnewapiserver, disruptionserviceloadbalancer, and others.
  • Framework handles NotSupportedError uniformly at every phase boundary (PrepareCollection, StartCollection, CollectData, ConstructComputedIntervals, EvaluateTests, WriteContentToStorage), converting to JUnit skips.
  • RetryWithExponentialBackoff used for the Infrastructure API call; MicroShift handled via IsNotFound.
  • Both deprecated APIServerInternalIP (singular) and current APIServerInternalIPs (plural) fields are checked for backward compatibility.
  • WriteContentToStorage returning w.notSupportedReason directly is correct: nil when supported, NotSupportedError when not.
  • No race condition on the notSupportedReason field: the framework calls phases sequentially per monitor test.
  • No variable shadowing issues in PrepareCollection.

Open questions for the author

  • Would it be worth also counting scanned haproxy containers (not just pods) and failing if zero were scanned? This would guard against a hypothetical container rename breaking collection silently.
  • The pre-existing // move to prepare? comment on StartCollection (line 71) — now that PrepareCollection does real work, is moving kubernetes.NewForConfig there a natural follow-up?
