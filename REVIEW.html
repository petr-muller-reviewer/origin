Needs discussion — The core logic (OKD detection, stream targeting) is correct and well-scoped, but the reorder of the ClusterVersion fetch to run before the MicroShift check risks breaking MicroShift runs of this test, based on how MicroShift detection and ClusterVersion usage are handled elsewhere in this repo. Worth confirming with the author before merge.

What this PR does

  • Adds OKD detection to the "should match os version" Ginkgo test in test/extended/ci/job_names.go, based on ClusterVersion.Status.Desired.Version containing okd-scos.
  • Fails the test if job name and cluster OKD-ness disagree on the okd-scos substring.
  • Threads isOKD and the already-fetched clusterVersion into validateStandaloneNodeOS.
  • OKD clusters now target the centos-10 OS image stream instead of falling through the RHCOS 9/10 heuristics used for OCP.

Findings

should-fixClusterVersion fetch moved ahead of isMicroShift check

test/extended/ci/job_names.go:184-194

The new ClusterVersions().Get(..., "version", ...) call (with o.Expect(err).NotTo(o.HaveOccurred())) now runs unconditionally, before the isMicroShift/isHyperShift branch. Previously this fetch only happened inside validateStandaloneNodeOS — i.e. only on the non-MicroShift/non-HyperShift path. Existing code in this repo treats "MicroShift" and "safe to fetch ClusterVersion" as mutually exclusive: test/extended/apiserver/api_requests.go:44-51 explicitly gates its ClusterVersion fetch behind !isMicroShift, and IsMicroShiftCluster's doc comment (test/extended/util/framework.go:2315-2325) explains MicroShift is detected via a microshift-version configmap rather than ClusterVersion, implying MicroShift doesn't reliably serve that resource. If so, this test will now hard-fail on MicroShift instead of reaching validateMicroshiftNodeOS's skip/short-circuit path as before.

clusterVersion, err := oc.AdminConfigClient().ConfigV1().ClusterVersions().Get(context.Background(), "version", metav1.GetOptions{})
o.Expect(err).NotTo(o.HaveOccurred(), "Error getting ClusterVersion version singleton")

isOKD := strings.Contains(clusterVersion.Status.Desired.Version, "okd-scos")
if isOKD && !strings.Contains(originalJobName, "okd-scos") {
    e2e.Failf("cluster is OKD but job name %q does not contain 'okd-scos'", originalJobName)
}
if !isOKD && strings.Contains(originalJobName, "okd-scos") {
    e2e.Failf("cluster is not OKD but job name %q contains 'okd-scos'", originalJobName)
}

isMicroShift, err := exutil.IsMicroShiftCluster(oc.AdminKubeClient())

questiondoes OKD always target centos-10 regardless of install version?

test/extended/ci/job_names.go:277-291 (validateStandaloneNodeOS)

For isOKD == true, the function hardcodes targetStream = "centos-10" unconditionally. Non-OKD clusters get a version-based fallback (4.x installs preserved as rhel-9 even after upgrade to 5.x) via the default: branch, but OKD skips that fallback entirely. If OKD ever had a pre-centos-10 stream, an OKD cluster on that older stream and not yet upgraded would fail this check. Not necessarily wrong, but unexplained in the PR description or code.

switch {
case isOKD:

case strings.Contains(jobName, "rhcos10"):

case strings.Contains(jobName, "rhcos9"):

case strings.Contains(jobName, "-runc"):

Things I checked and was fine with

  • originalJobName (pre e2e- split) vs jobName (post-split) usage: using originalJobName for the okd-scos match is correct since okd-scos appears in the job-name prefix, before the e2e- marker.
  • switch precedence in validateStandaloneNodeOS: the isOKD case correctly takes precedence over the rhcos10/rhcos9/-runc substring checks, avoiding misclassification of an OKD job name that also happens to contain e.g. rhcos10.
  • No unit tests expected/needed — this is itself a live-cluster e2e assertion, consistent with the rest of the file.
  • No changes to shared library code or other call sites; blast radius limited to this one Ginkgo It.

Open questions for the author

  • Does MicroShift reliably serve the config.openshift.io/v1 ClusterVersion "version" singleton? If not, the reordered fetch will break MicroShift runs of "should match os version" — can you confirm, or move the fetch back inside the standalone branch?
  • Has OKD ever used a stream other than centos-10 (e.g. during an internal 9→10-style transition)? If not, might be worth a one-line comment explaining why the version-based fallback is skipped for OKD.
