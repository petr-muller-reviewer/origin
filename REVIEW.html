VERDICT: APPROVE

This is a narrowly scoped, correct fix for a real resource leak observed in CI (the linked aggregated GCP upgrade run where a Gateway API precheck failure left a Gateway deployment behind). The recover/re-panic pattern is textbook-correct, is exercised by a solid table-driven unit test covering all panic combinations, and the companion guard in the Gateway API test is a necessary fix for a nil-pointer panic the main change would otherwise introduce — not scope creep. Build, vet, and tests all pass.

What this PR does

  • Extracts runUpgradeTest in disruption.go, registering Teardown via a deferred recover before Setup runs, instead of deferring it only after Setup returns successfully.
  • Uses a recover/re-panic pattern so a panic inside Teardown never masks the original setup/test panic.
  • Adds a guard in GatewayAPIUpgradeTest.Teardown for the case where Setup panics before t.oc/t.gatewayName are initialized — otherwise Teardown would nil-pointer-panic now that it can run in that scenario.
  • Adds disruption_test.go with table-driven coverage of setup/test/teardown panic combinations.

Nits

Nit Discarded teardown panic is not logged
test/extended/util/disruption/disruption.go:189-193

When a primary (setup/test) panic already occurred, a subsequent panic from Teardown is silently discarded via _ = recover(). This is intentional — it avoids masking the real failure — but it means a genuine teardown-time resource leak in that specific path goes completely unreported. Consider an e2e.Logf call before discarding, purely for diagnosability.

// A teardown panic must not replace the setup or test failure.
defer func() {
    _ = recover()
    panic(primaryPanic)
}()
test.Teardown(ctx, f)

Things I checked and was fine with

  • gofmt -l clean on all three changed/added files.
  • Traced all 6 panic-combination cases in disruption_test.go by hand against runUpgradeTest — call order and surfaced panic value match expectations in each case.

  • GatewayAPIUpgradeTest.Teardown guard is scoped correctly: t.oc and t.gatewayName are set contiguously early in Setup, and the only panic point before that is the o.Expect(t.precheckErr) check at the top of Setup. All other delete calls in Teardown already tolerate missing resources via IsNotFound/--ignore-not-found, so the new guard covers exactly the previously-unhandled gap.
  • Confirmed the Gateway API guard is a necessary companion change, not scope creep: without it, the disruption.go fix would introduce a nil-pointer panic in GatewayAPIUpgradeTest.Teardown for the exact failure mode (setup panics before resource init) it's meant to fix.
