Verdict: Approve. Clean, well-tested addition. The sweep-line algorithm is correct, edge cases are covered by unit tests, and prior review feedback from dgoodwin has been addressed. CI confirms 22/22 passes. No blocking issues found.

What this PR does

  • Adds findFullAPIOutageWindows(): a sweep-line algorithm that takes existing OnPremHaproxyDetectsDown intervals and finds time windows where a single haproxy instance saw ≥3 kube-apiserver backends down concurrently (full API outage for HA clusters).
  • Adds evaluateFullAPIOutages(): produces a new JUnit test that hard-fails (not flaky) on any post-install full outage. The first outage per haproxy instance is tolerated as the expected install-time state.
  • Refactors EvaluateTestsFromConstructedIntervals to build a result slice and append the new test alongside the existing (still flaky) per-backend reachability test.
  • Cleans up commented-out code and improves the existing test's failure message per prior review feedback.
  • Adds comprehensive unit tests covering the sweep semantics and JUnit evaluation logic.

nit Pre-existing ___ key packing

pkg/monitortests/network/onpremhaproxy/monitortest.go:261

pairKey := interval.Locator.Keys[monitorapi.LocatorOnPremKubeapiUnreachableFromHaproxyKey]
parts := strings.SplitN(pairKey, "___", 2)

Packing two locator keys into one string with a ___ separator is fragile. This is pre-existing from ConstructComputedIntervals (line 113) and not introduced by this PR. dgoodwin raised this in review; mkowalski explained it is a limitation of the locator struct type (map[LocatorKey]string — no nested maps). Not actionable in this PR but worth tracking as tech debt.

question Install-tolerance assumption

pkg/monitortests/network/onpremhaproxy/monitortest.go:341-343

for _, window := range outagesPerNode[node][1:] {

The [1:] skip assumes the first outage window for every haproxy node is always the install phase. If a haproxy pod restarts mid-run and that restart causes a brief full outage that happens to be the first window for a "new" node entry, it would be silently tolerated. This seems acceptable given the monitoring setup (the node name stays the same across pod restarts, so its install-phase window would still be first), but worth confirming with the author.

Things I checked and was fine with

  • Sweep algorithm correctness: tie-breaking sorts recovery events (delta: -1) before down events (delta: 1) at equal timestamps, correctly preventing artificial overlap at second-granularity boundaries.
  • Window merge logic: !window.from.After(merged[len(merged)-1].to) correctly handles both touching and overlapping windows.
  • [1:] slice safety: findFullAPIOutageWindows only adds a node to the result map when len(merged) > 0, so the slice passed to [1:] is guaranteed non-empty.
  • Intentionally non-flaky: the new test returns only [failure] (not [failure, success]), making it a hard fail. This is the correct design choice for a full API outage.
  • Existing behavior preserved: the per-backend flaky test continues to emit the [failure, success] pair exactly as before.
  • Unit test coverage: edge cases for no intervals, single/two/three backends, cross-node isolation, two separate outages, same-second boundary, backend flapping within outage (merged), per-instance tracking, install tolerance, post-install failure, partial post-install outage.
  • CI signal: TRT bot reports 22/22 passes for the new test.
  • Prior review feedback addressed: commented-out lines removed, test name updated to "should not encounter" (dgoodwin suggestion), failure message improved.

Open questions for the author

  • Is there a scenario where a haproxy node appears in the monitoring data without the install-phase outage being its first window? For example, a haproxy pod restart or node replacement mid-test where the node name changes and the "new" node's first observed window is actually a real outage, not install.
